# Implemented API Contract

## Transport

HTTP protocol 0.1.0. Domain calls use `POST /api/tools/OPERATION` with a single JSON object, `Content-Type: application/json`, and a complete body limit of 1 MiB. Authentication uses `Authorization: Bearer TOKEN` or the HttpOnly SameSite=Strict session cookie. Browser origins must match the server. Sessions expire after 12 hours and are stored as token hashes. Production TLS termination must preserve trusted transport semantics; this phase binds localhost by default.

All routes reject unconfigured HTTP Host headers with 421, before authentication/assets. Loopback IPs and localhost are trusted by default; `serve --public-host HOST` explicitly adds a bare browser hostname. Browser Origin must match the request host and actual transport scheme; forwarded headers are not trusted implicitly. This prevents a matching attacker-controlled Host/Origin pair from accessing loopback endpoints through DNS rebinding.

Responses use the operation's JSON result. Failures use `{"error":{"code":"stable_code","message":"human-readable explanation"}}` with 400 invalid input, 401 authentication, 403 authorization, 404 unsupported/missing, 409 version/state conflict, 413 payload limit, 415 media type or 429 sign-in throttling. Unexpected failures return a generic 500 and a server log entry. Unknown fields are rejected on typed requests. No API returns password hashes.

## Operations

| Operation | Input | Result | Authority |
| --- | --- | --- | --- |
| `login` | `{username:string,password:string}` | `{token:string,account:{id,username,administrator,suspended}}` plus cookie | Public; password verified; throttled |
| `getSession` | `{}` | `{account,installationId:string,revision:integer,settings:{version,agents,registrations,handbrake,executionMode},preferences:Preferences}` | Current session; preferences share the authenticated snapshot |
| `logout` | `{}` | `{signedOut:true}` | Revokes current session only |
| `listWorkflows` | `{}` | `{items:Workflow[],nextCursor:""}` | Current session; two seeded definitions in P01 |

`Workflow` is `{id:string,version:integer,title:string,family:"human"|"agent",published:boolean,phases:Phase[],rules:Rule[]}`. `Phase` has string `id,title,role,instructions` and boolean `agentic`. `Rule` has string `id,source,outcome`, optional string `target,action`, integer `priority` and optional string-map `conditions`. The human definition's main path is Todo/Doing/Done; agent Doing displays as Implementation. The published seed versions are immutable.

Public discovery: `GET /healthz`, `/openapi.json`, `/api/actions`, `/skill.md`; browser assets `/`, `/app.js`, `/style.css`. No domain database access is available over the client surface. OpenAPI publishes input/result/error schemas for every registered operation; the exact request/result contract above is normative for this build.

## Projects and human tickets

`createProject` accepts `{name,key?,requestId}` and atomically returns a project, creator Maintainer membership and protected Unassigned goal/epic IDs. Keys are lowercase ASCII letters/digits/underscore/hyphen, 1–80 characters; names are 1–200 bytes. Stable creation `requestId` is mandatory (1–100 bytes), scoped to actor and operation; matching retries return the original result, conflicting reuse returns 409. `createTicket` accepts `{projectId,parentId?,kind?,title,description?,criteria?,agent?,priority?,requestId}`; omitted kind/intent/priority are task/agent/medium. Parent defaults are project-local; wrong types/projects/hidden immediate parents fail.

`listProjects` and `listTickets` return `{items,nextCursor}`. Default limit is 100, maximum 200; cursors encode the last ID and results are ordered ascending. Ticket filters: `projectId,kind,agent,status,query,includeHidden`. All pages enforce current project rights. `getTicket` takes `{id}`. `listTicketHistory` takes `{id,cursor?,limit?}` and returns immutable snapshots in ascending version order.

`updateTicket` takes `{id,expectedVersion}` and optional title/description/criteria/priority/labels/start/eta/due/progress fields. Omission preserves values; empty text/date clears where valid. Content changes require preexisting Todo; protected default titles cannot change. Dates use YYYY-MM-DD, ETA cannot precede start. Scalar agent progress is a report; human status uses explicit transitions in this phase. No-op edits create no revision.

`transitionTicket` accepts `{id,expectedVersion,target,confirm?}` for declared human routes. Done requires explicit `confirm:true` and records current criteria/actor/time/basis. Agent transitions refuse this generic route. Nonempty containers derive completion from non-deleted children; archived children still count. Percentage rounds to the nearest integer. Empty containers remain incomplete; epic open planning prevents Done. Every mutation reconciles its affected hierarchy within the same SQL transaction. Stale writes return 409 without partial changes. Current Contributor-or-higher rights are required to create/edit tickets; Viewers read only.

The generated OpenAPI contains complete concrete project/ticket/history and operation schemas. UI and CLI call the same tool routes. Alias names such as `createProject` and `listTicketHistory` map to the corresponding canonical specification actions.

## Work controls

`setDependencies` takes `{id,expectedVersion,dependencies:integer[]}` on unclaimed Todo tasks/epics, up to 200 direct IDs. New references must be unique same-project non-cancelled tasks/epics. Existing cancelled prerequisites remain blockers. Validate effective inherited prerequisites plus hierarchy-completion edges as one acyclic dependency graph; workflow cycles remain valid and separate. Human Doing/Done requires completed prerequisites.

`cancelTicket` takes `{id,expectedVersion,reason?}`. Tasks cancel individually; containers cancel themselves and unfinished descendants, including hidden work, with one correlation ID. Done/already-cancelled descendants remain intact. `reopenTicket` takes `{id,expectedVersion}` and affects only the selected record. Agent tasks and containers require Maintainer; human tasks require Contributor. Agent reopening is inactive Todo with retained history and a resume hold. Containers recompute current child completion.

`setTicketVisibility` takes `{id,expectedVersion,archived?,deleted?}` and requires Maintainer. Change only the selected record, preserve children and reject protected defaults or pending execution. Restore retains status and adds an agent resume hold. `transferTicket` takes `{id,expectedVersion,destinationProjectId,parentId?}` and requires current Maintainer authority in both projects, or installation administrator. Move the complete subtree including hidden descendants atomically, preserving IDs/history/pins; reject protected/busy records, incompatible assignees, invalid parents or resulting cross-project prerequisites. Omitted parents use destination defaults. `moveTicket` takes `{id,expectedVersion,parentId}` for same-project valid reparenting with Contributor rights.

`changePassword` takes `{currentPassword,newPassword}`, verifies the current password, requires 12–1,024 new-password bytes and revokes all account sign-in sessions atomically. It returns `{signedOut:true}` and requires a fresh sign-in. The combined visibility and container-cancellation routes compose their corresponding permanent action variants; API discovery names the primary action.

## Workflow definitions

`listWorkflows` accepts `{projectId?,cursor?,limit?}` and returns authorized definitions ordered by exact key; its cursor is the last opaque workflow key. `getWorkflow` accepts `{workflowKey,ticketId?}`. Optional ticket context grants access only to that currently authorized ticket's exact retained pin, including after transfer. Published keys are `ID@VERSION`; mutable drafts use `ID@draft`. Definitions add `projectId,draftRevision,layout?` to the seed shape; layout maps phase IDs to bounded `{x,y}` coordinates.

`copyWorkflow` takes `{sourceKey,projectId,title,requestId}` and creates a new draft identity. `draftWorkflow` takes `{workflowKey}` and idempotently starts the next version of that same definition. `saveWorkflow` takes `{definition,expectedRevision}`, preserving identity/family/ownership and rejecting stale writes. `deleteWorkflow` takes `{workflowKey,expectedRevision}` for drafts only; published history remains retained. Maintainer authority controls project definitions; installation drafts require administrator authority. Save validates the whole graph, including disconnected branches, exact destinations, manual role gates and overlapping conditions. Declared cycles and self-retries are valid.

Rules match source/outcome and exact string conditions on `reason,revisionKind,questionOrigin,result`. Lower numeric priority wins (0–10,000); potentially overlapping matches at equal priority fail validation. Choose exactly one target or `wait`/`halt` action. `previewWorkflowOutcome` takes `{workflowKey,source,outcome,context?}` and returns `{ruleId,target?,action?,needsAttempt,requiredGates}` without state changes. An unmatched route returns 409 with a routing-specific code.

`activateWorkflowVersion` takes `{workflowKey,expectedRevision,projectId,expectedProjectVersion}`. It validates complete agent/human routing, publishes an immutable version if needed and updates only that project's selection for new tickets. Existing pins remain unchanged. Installation-wide future-project default selection is not shipped yet. `previewWorkflowMigration`/`migrateWorkflow` take `{sourceKey,targetKey,tickets:[{id,expectedVersion}],mapping:{sourcePhaseId:targetPhaseId}}`. Migration requires current Maintainer rights, stopped/unclaimed work, published same-family definitions and exact same-role mappings; the complete batch commits or fails together. No automatic queueing or acceptance occurs. Full agent continuation/migration guards depend on the later execution phase.

New tickets use a unique Todo phase in their selected pin, or explicit `phaseId` when required. Human transitions accept exact target IDs (or a uniquely resolved semantic role), with optional explicit `outcome,context` for configured rules. Display titles never grant authority.

## Deterministic demo execution

`setExecutionMode` accepts `{mode:"off"|"demo",expectedVersion}` using `getSession.settings.version`; administrator only. Saved mode is honored at server startup. Demo mode executes deterministic in-process outcomes every 500 ms, with zero model calls, OS-process claims or source writes. It is distinct from real Codex execution. Shared per-project pools default to one Refine/Doing worker; `setLaneCapacity` accepts `{projectId,expectedVersion,refineWorkers,doingWorkers}` in 0–20. `setHandbrake` accepts `{projectId?,expectedVersion,workflowKey?,phaseId?,engaged}` for administrator system or Maintainer project/stable-phase controls. Its result is the changed Settings or Project object.

`requestRefinement` takes `{id,expectedVersion}` on a visible unclaimed agent Todo task/epic. A successful Refine result retains original content and proposes an exact scope/basis. `acceptRefinement` takes `{id,expectedVersion,proposalId,decompose?}`; human Contributor-or-higher acceptance enters Ready or Decompose. Task decomposition promotes in place and closes planning after atomic Todo child creation. Open epic planning remains separate from child delivery rollups; closed container rollups never become executable implementation work.

`runDemoStage` accepts `{id,expectedVersion,requestId,outcome?,question?}`, with success/failure/question outcomes. Results are `{ticket,simulated:true,attemptId?,blockedReason?}`. Each new automated visit consumes one cumulative attempt (default 20); matching request retries do not rerun it. Questions save origin/workflow/basis and retire the in-process adapter immediately without inventing an OS exit. `answerQuestion` takes `{id,expectedVersion,questionId,answer}` and resumes the unchanged origin under the same attempt; a configured different destination counts anew. Unknown/live external execution remains blocked rather than adopted by the demo adapter.

Declared `wait`/`halt` actions persist `routingHold` and prevent automatic retries. Scope acceptance and question answers clear only their applicable wait; an explicit resume may retry a held ordinary phase under normal gates and a fresh counted attempt. Equal-priority scheduling uses durable `phaseEnteredAt` (creation time for older records), then stable ID. Unrelated metadata, version migration and polling do not reset it; unchanged-origin question continuation retains its saved waiting basis.

`setExecutionBudget` accepts `{id,expectedVersion,limit,resume?}` from a Maintainer, 1–1,000 total attempts, preserving consumption. An unbudgeted next attempt records a visible block and resume hold; the last admitted attempt may complete. `pauseTicket`/`resumeTicket` take `{id,expectedVersion}` and retain independent guards. Pending unsuspended question continuations block migration/transfer/visibility changes until separately paused.

Demo Implementation/Review results contain no real commit/check evidence. Review is read-only and separately recorded; simulated evidence cannot satisfy `approveTicket`. `rejectTicket` accepts `{id,expectedVersion,revisionKind:"implementation"|"scope",feedback?,confirm?}` and uses the declared Ready/Todo revision path without implicit acceptance or reset.

## Local Git delivery

`configureLocalRepository` accepts `{projectId,expectedVersion,repository,storageRoot}` from an installation administrator. Both paths are absolute; the repository must have a committed `main` checkout and storage must be outside it. Rebinding retained execution/artifacts is refused. These host operations remain single-account only until isolation is verified; demo execution must be off.

`prepareTaskWorktree` accepts `{id,expectedVersion,requestId}` on an eligible Ready agent task. It requires current accepted scope, completed prerequisites, finite attempts and applicable capacity/handbrakes. An ownership manifest identifies a retained task branch and worktree; existing unowned paths are never reused. `recordTaskDelivery` accepts the same fields plus optional `reportedChecks` and captures the actual clean, committed, linear candidate against its pinned base. Controller checks currently mean Git whitespace validation only. Operator-reported check text remains separately labelled. No harness execution or real Review is invented.

`approveTicket` takes `{id,expectedVersion,confirm:true}` from a Maintainer/administrator at human Approval. It checks exact scope, binding, prerequisites, candidate/check fingerprint and every configured Review gate, then fast-forwards clean `main` with hooks/filters disabled and ignored-file overwrite protection. Done records the actual integrated candidate and immutable agreement basis. The seeded workflow still requires a real successful candidate-bound Review; a deliberately published workflow may omit Review while retaining human Approval. Stale main, dirty worktrees and conflicts preserve retained work and refuse integration. Automatic Rebase and cleanup are not shipped.

Git calls reserve durable intent, run commands outside SQL write transactions, record controller-owned exit facts and revalidate before finalization. Matching request receipts fence retries. `reconcileGitOperation` accepts `{id,expectedVersion}` from a Maintainer to inspect retained facts after a durably verified command exit. It preserves status and stop intent; unknown exit blocks replacement. A directory or branch never proves a process has exited. Full crash recovery is not claimed.

`getTicketAgreements` accepts `{id}` and returns current/saved scope hashes, staleness and criteria. Repository-binding changes invalidate readiness. `markReady` accepts `{id,expectedVersion,basis,confirm:true}` to explicitly re-agree previously accepted stopped Ready work against its exact current basis. `rejectRefinement` accepts `{id,expectedVersion,reason?}` and follows the declared failure route without changing original content. Completion revisions freeze project/workflow, prerequisite versions, container child versions where derived, and actual commit/base where present. Correlated ticket revisions carry the originating installation transaction revision.

## Human Ideas contract

Ideas use a separate monotonic `idea:N` identity. `saveIdea` takes `{id?,expectedVersion?,projectId?,title,text,requestId?}`; creation chooses private inbox when projectId is omitted/zero, while updates cannot change placement. Inbox read/write belongs to creator/administrator; project reads require Viewer and edits require Contributor. `listIdeas` accepts `{projectId?,inboxOnly?,query?,includeHidden?,cursor?,limit?}`; zero project with inboxOnly false combines only currently authorized placements. `getIdea` takes `{id}` and bounds recent detail to 20 proposals/20 acceptances/200 links with `hasOlder`. Paged `getIdeaHistory`/`getIdeaLinks` take `{id,cursor?,limit?}`. History proposal IDs resolve through `getIdeaProposal` with `{id,proposalId}`, returning exact retained proposal/acceptance. `getTicketIdeas` uses `{id,cursor?,limit?}` and a normal page result. All histories and proposal/link navigation recheck current placement rights.

`submitIdeaProposal` takes `{id,expectedVersion,requestId,targets}` within 96 KiB and creates an immutable human proposal against that exact Idea version without editing source content. Each of 1–20 targets selects either `{existingId,existingVersion}` or `{create:{projectId,parentId?,kind?,title,description?,criteria?,agent?}}`. Existing references and destination projects must be authorized. This initial grammar uses existing/default parents; within-proposal parent references and agent curation remain pending.

`acceptIdeaProposal` takes `{id,expectedVersion,proposalId}`. Current human source editing and Contributor rights in every current target are rechecked in one transaction. New records start ordinary Todo; existing records retain status/content/version. Acceptance/provenance and all creates commit together. Proposal identity fences repeats, returning its original acceptance without duplicate work, subject to current source/target rights. Hidden Ideas must first be restored. A later source edit makes an unaccepted proposal stale; historical acceptance stays visible. Links are stored bidirectionally and read through `getTicketIdeas`/`getIdea`, with inaccessible endpoints omitted.

`previewIdeaPlacement` and `setIdeaPlacement` take `{id,expectedVersion,projectId,confirm?}`. The preview explains publication of retained content/history; set requires confirm true. Source project Maintainer or inbox owner/administrator plus destination Contributor rights are required. Return to creator inbox requires creator/source Maintainer or administrator. `setIdeaVisibility` takes `{id,expectedVersion,archived?,deleted?}` with those same source control rights. Active/unknown curation blocks placement/visibility. Changes preserve identity/history/accepted links and never mutate or start linked tickets. Proposals and acceptance have independent retained records; source revisions have transaction correlation.

## Graph and personal presentation contract

`getGraph` accepts `{projectId?,query?,kind?,agent?,maxNodes?}` and returns authorized unique `project:N`/`ticket:N` nodes, hierarchy/dependency edges, required context ancestors and a separately versioned layout. Default/maximum node limits are 1,000/2,000; oversized selections fail explicitly and must be narrowed. Context nodes retain current project authorization, including hidden required ancestors. `saveGraphLayout` accepts `{projectId?,expectedVersion,positions:{nodeId:{x,y,z}}}` as a bounded patch (maximum 2,000 finite coordinates within ±100,000). Project scope publishes shared coordinates with Contributor-or-higher rights; project-zero scope saves only the current actor's private All projects arrangement, including Viewer navigation arrangements. Recheck every node's current scope/access and layout version atomically. Layout changes never revise tickets, relationships or scheduling.

`getAppearanceStyles` discovers bundled `paper` and `instrument` styles plus `light`/`dark` modes. `getViewPreferences` reads the current account's `{version,style,mode,defaultView,defaultProject,recent}`. `setAppearance` takes `{expectedVersion,style,mode}` and edits only appearance; `saveViewPreferences` takes `{expectedVersion,defaultView,defaultProject,recent}` and edits only navigation. Both share optimistic preference versioning, are available to owners regardless of project role, and never accept another account ID. Recent contexts are bounded to 20 `{view,projectId,ticketId?}` entries. Validate referenced resources against current rights on save and sanitize inaccessible retained defaults on read. Preferences affect future defaults and presentation; polling never redirects an active client or overwrites its foreground editor. Live Graph camera/selection and anonymous appearance remain local and are cleared on account switch.

## Execution capability inspection

`getEffectivePermission` accepts `{projectId,adapter,command}` from a current project Viewer-or-higher. The command is an argv array of 1–128 strings, each within 4 KiB and 64 KiB combined. Initial adapter IDs are `codex-structured` and `codex-pty`. The response is a non-executing inspection: `{allowed:false,executable:false,winningRestriction,policyVersion,capabilities}`. Both native adapters remain blocked for missing verified per-operation dispatch/recovery enforcement. Inspection neither runs a command, reserves work, changes a grant nor authorizes a later dispatch. The installed-version/schema probe is a separate development tool and cannot enable an adapter.

## Storage envelope

Schema 1 stores a versioned installation aggregate transactionally in the selected SQL backend. A serialized server owns mutations and snapshots; PostgreSQL additionally locks the row. SQLite uses WAL and an exclusive OS installation lock; PostgreSQL uses a connection-held advisory lock. All PostgreSQL domain reads/transactions use that same retained connection. Losing it fails closed rather than reconnecting without ownership. Unsupported schema versions refuse operation; cancellation/outage errors remain distinct from missing initialization. The aggregate is an initial local implementation, not a claim of large-workspace performance. Clients do not import the store. This representation may migrate behind stable domain contracts as capacity evidence requires.
